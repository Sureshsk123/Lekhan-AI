# Enhanced Mochawesome Reporting

This document explains the custom enhancements added to the Mochawesome HTML reports generated by the Selenium Enterprise Automation Framework.

## Context Injection Strategy

The native Mochawesome report has been heavily customized to provide deeper insights without needing to dig into terminal logs or separate Excel files. We leverage the `mochawesome/addContext` module inside `tests/BaseTest.js`.

For **Every Test**, we inject:
- Target Browser
- Execution Environment
- The assigned Worker ID
- Execution Timestamp
- Unique Execution ID
- Clickable relative links directly to the Excel Report (`E2E_Report.xlsx`) and the raw log file (`automation-worker-[id].log`).

For **Failed Tests**, we additionally inject:
- The `Current URL` at the time of failure.
- A raw dump of the **Browser Console Logs**.
- The explicit **Stack Trace** (in addition to the error message).
- **Inline Base64 Screenshots**: Screenshots are pulled directly from the WebDriver stream when a failure is caught, and embedded seamlessly inside the HTML using a Base64 data URI (`data:image/png;base64,...`).

## Failure Categorization (JSON Manipulation)

When running tests in parallel, Mochawesome generates independent JSON report shards (`report-0.json`, `report-1.json`, etc.). 

1. **Merge Phase**: Using `utilities/GlobalTeardown.js`, we hook into Mocha's `mochaGlobalTeardown` to merge all these files via `mochawesome-merge`.
2. **Grouping Phase**: The `MochawesomeManager.groupFailures(json)` method scans the merged JSON tree for any test that failed.
3. **Virtual Suites**: It dynamically builds a virtual root suite named `"Failures by Category (Aggregated)"`. Based on keyword matching in the test titles (e.g. `auth`, `login`, `ui`, `workflow`), it clones the failed tests into grouped sub-suites (Authentication, Forms, Navigation, UI, Business). 
4. **Injection**: This virtual suite is injected at the top of the JSON payload so that it is the first thing visible in the HTML report.

## Execution Badges
Before generating the HTML report, `MochawesomeManager` iterates through every test record and injects HTML `<span>` tags directly into the `test.title`. This natively forces Mochawesome to render colorful execution badges next to every test indicating the execution status (Passed/Failed), the Target Browser (e.g., CHROME), the Worker ID, and the Target Environment (e.g., DEV).

## Post-Processing Dashboard & Performance Metrics
Mochawesome does not natively support injecting complex HTML layouts at the top of the body. To achieve this, the `MochawesomeManager` intercepts the generated `mochawesome.html` immediately after `marge.create()` completes. It uses regular expressions to inject:
1. **Enterprise Dashboard**: A grid-based layout above the React root showing Framework details, Environment, Execution IDs, and overall Execution Stats.
2. **Performance Metrics**: A custom CSS flexbox distribution card outlining Browser Distribution, Average Test Times, Total Duration, and a graphical pass/fail progress bar.
3. **Enterprise Footer**: A custom footer injected securely at the bottom of the HTML payload.

## Cross Report Linking
- **Mochawesome Context**: Every executed test includes relative paths to `../../reports/E2E_Report.xlsx`, its explicit worker log (`../../logs/chrome/...`), and relative screenshot paths.
- **ExcelJS Reports**: `ExcelReportManager` uses the native ExcelJS Hyperlink property to dynamically construct clickable relative links in all output cells, seamlessly cross-linking the Excel Report back to `mochawesome.html`, the screenshot directory, and the raw `.log` text files.

## Retry Visualization (Heuristic Parsing)
Since `RetryUtility` does not maintain a global execution state, `BaseTest.js` intercepts its output dynamically. During the `afterEach` teardown, it accesses the current worker's `.log` file, searches for the precise test execution block, and parses out any `Action failed on attempt X/Y` statements. This retry trace is then formatted and appended into the Mochawesome context (e.g., "Attempt 1 ❌ Failed").

## CI Compatibility
All paths are dynamically constructed utilizing the `process.cwd()` root relative pointers. The combination of `mochawesome-merge` running safely on the master thread guarantees that distributed execution across CI nodes (or local parallel threads) resolves deterministically.

## Future Extension Points
- **Jira/XRay Integration**: The contextual JSON manipulation phase (`groupFailures` or `injectBadges`) in `MochawesomeManager` could easily be augmented to cross-link test IDs directly to Jira via API mapping.
- **Trend Analysis**: By pushing the execution JSON blocks into an S3 bucket before the `HTML` post-processing phase, historical trends can be generated.
